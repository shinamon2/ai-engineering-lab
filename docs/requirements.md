## 1. 想定利用者とユースケース

| 利用者 | 状況 | 得たいもの |
|---|---|---|
| 開発者本人（主） | 技術習得・デモ | LLM 連携・評価の一連の流れを動かして確かめる |
| 閲覧者（レビュアー・採用担当など） | ポートフォリオの確認 | 設計判断・品質の測り方・コスト意識を短時間で理解する |
| 架空の PM / エンジニア（想定ペルソナ） | チケット着手前 | 不明点・影響範囲・テスト観点の叩き台 |

### 代表ユースケース（UC）

- **UC-1**: チケットのタイトルと本文を入力して「分析」を押すと、6 項目の分析結果が表示される
- **UC-2**: 架空のサンプルチケットを選んで分析を試せる
- **UC-3**: 分析結果を Markdown / JSON としてコピーできる
- **UC-4**（Phase 2）: 影響範囲・不明点に、根拠となった架空仕様書の出典が表示される
- **UC-5**（Phase 3）: 分析が複数ステップで進み、どのステップで何をしたか（実行経過）が見える
- **UC-6**（開発者向け）: コマンド 1 つで評価データセット全件を分析し、スコアを確認できる
- **UC-7**（Phase 6）: 架空チケットを入力して実行開始を承認すると、隔離された作業場所のダミーリポジトリで「実装 → テスト → 最大 3 回の修正」が自動で進み、差分・テスト結果・費用・停止理由を確認できる

#### 停止条件・承認・実行履歴の定義

| 項目 | 定義 |
|---|---|
| 停止条件 | テスト成功（`TESTS_PASSED`）、修正 3 回到達（`MAX_FIX_ATTEMPTS`）、同じ失敗の 2 回連続（`REPEATED_FAILURE`）、費用上限（`BUDGET_EXCEEDED`）、時間上限（`TIMEOUT`）、ターン数上限（`MAX_TURNS`）、利用者の中断（`USER_CANCELLED`）、承認の却下（`APPROVAL_REJECTED`）、隔離を確認できない（`SANDBOX_UNVERIFIED`）、実装役のエラー（`AGENT_ERROR`）、テスト基盤のエラー（`TEST_INFRA_ERROR`）、分析のエラー（`ANALYSIS_ERROR`） |
| 承認① | 実行開始前。分析結果・対象のダミーリポジトリ・予算を人が確認する |
| 承認② | 終了後。差分とテスト結果を人が確認する。MVP では本体への取り込み機能そのものを作らない |
| 実行履歴 | 実行ごとに保存し、どの停止理由で終わったかを必ず残す |

## 3. 出力仕様（Phase 1 の分析結果スキーマ・案）

Zod スキーマを**単一の正**（SSOT: Single Source of Truth）とし、LLM への応答形式の指定（JSON Schema）・API 応答の検証・UI の型・評価の入力を、すべてここから導出する設計です。

```ts
// 案。項目名・上限値は Phase 1 の実装開始時に確定する（ANL-U1）
const AnalysisResult = z.object({
  summary: z.string().max(400),                       // チケットの一文要約
  requirements: z.array(z.object({                     // ① 要求の整理
    statement: z.string(),
    acceptanceCriteria: z.array(z.string()),
  })).max(10),
  openQuestions: z.array(z.object({                    // ② 不明点
    question: z.string(),
    reason: z.string(),                                // なぜ確認が必要か
    priority: z.enum(["high", "medium", "low"]),
  })).max(10),
  impactAreas: z.array(z.object({                      // ③ 影響範囲
    area: z.enum(["ui", "api", "db", "auth", "external", "infra", "other"]),
    description: z.string(),
    confidence: z.enum(["high", "medium", "low"]),
  })).max(10),
  testPerspectives: z.array(z.object({                 // ④ テスト観点
    category: z.enum(["normal", "error", "boundary", "security", "performance", "regression"]),
    perspective: z.string(),
  })).max(20),
  estimate: z.object({                                 // ⑤ 工数見積もり補助
    tasks: z.array(z.object({ name: z.string(), hoursMin: z.number(), hoursMax: z.number() })).max(15),
    assumptions: z.array(z.string()),                  // 見積もりの前提
  }),
  risks: z.array(z.object({                            // ⑥ リスク
    risk: z.string(),
    severity: z.enum(["high", "medium", "low"]),
    mitigation: z.string(),
  })).max(10),
});
```

**設計上のポイント**

- 配列に上限を設け、出力トークン（＝費用）と表示崩れを抑える
- 列挙型（enum）を多用し、評価で機械的に照合できるようにする
- 見積もりは単一値ではなく「最小〜最大の幅＋前提」で表し、確定値ではないことを構造で示す
- 「わからない」を表現できるよう、不明点と確信度（confidence）を必須にする（もっともらしい断定を減らす）
- Claude API の構造化出力では、件数・文字数・数値範囲の制約を API 側で強制できない（公式の記載）。**上限値の最終的な強制は、必ずアプリ側の Zod 検証で行う**

## 4. 非機能要件（NFR）

|---|---|---|---|
| NFR-01 | 性能 | 分析 1 回の応答時間 | p95 で 30 秒以内（Phase 1） |
| NFR-02 | 費用 | 開発・運用費 | プロジェクト全体の共通予算として月 $10 を目標とする。アプリ側で止めるための目標であり、請求額の上限を保証するものではない |

| NFR-05 | セキュリティ | 実データ・個人情報を扱わない | ダミーデータのみ。入力欄に注意書きを表示 |
| NFR-06 | 品質 | 出力のスキーマ適合率 | 評価データセットで 98% 以上（再試行込み） |
| NFR-07 | 品質 | 単体テスト・E2E テスト | LLM は Mock で実行し、全件成功 |
| NFR-08 | 保守性 | LLM 提供元の差し替え | LLM 呼び出しを 1 つのインターフェースに閉じ込める |
| NFR-09 | 可観測性 | 呼び出し記録 | トークン数・所要時間・成否・モデル名を記録（入力本文は記録しない） |
| NFR-10 | アクセシビリティ | 基本対応 | キーボード操作・ラベル付与・色だけに依存しない表示 |
| NFR-11 | 公開性 | リポジトリを公開できる | 秘密情報スキャンで検出 0 件 |
| NFR-12 | 費用（Phase 6） | 1 実行・1 日の費用上限 | 1 実行 $1（目標）、1 日 $3。月 $10 は NFR-02 の共通予算に含む |
| NFR-13 | 性能（Phase 6） | 実行時間の上限 | 1 回の実装・修正 10 分、1 回のテスト 2 分、1 実行全体 30 分（初期値） |
| NFR-14 | セキュリティ（Phase 6） | 隔離が確認できない場合の扱い | 実装役を起動しない（fail closed） |
| NFR-15 | セキュリティ（Phase 6） | 実装役の操作範囲 | 作業場所の中のファイル操作と、許可リストのコマンドだけ。push・PR 作成・デプロイはしない |
| NFR-16 | 品質（Phase 6） | ループ自体のテスト | Mock の `CodingAgent` で、状態遷移・停止条件をすべて費用 0 でテストできる |
| NFR-17 | 保守性（Phase 6） | モデル名 | コードに直接書かず、設定で切り替える |

## 5. 制約条件

- 実在の組織の実データ・個人情報・非公開資料・非公開ソースコードを一切使用しない
- 完全なダミーデータのみを使用する（サンプルチケット・架空仕様書はすべて創作）
- 外部への送信は LLM API への分析依頼だけに限定する（分析ログの外部送信は行わない）。Phase 6 では、実装役（Agent SDK）から Claude API への通信が加わる。それ以外の外部ネットワーク接続は禁止する
- 認証情報をフロントエンドに配置しない

## 6. 決定事項・未決定事項

### 決定事項

| ID | 決定内容 | 判断理由 |
|---|---|---|
| RQ-01 | 出力は Zod スキーマで定義した構造化 JSON | 型安全・検証・評価を 1 つの定義で成立させるため |
| RQ-02 | スキーマ不正時は 1 回だけ再試行 | 無制限な再試行は費用が膨らむため。上限付きで信頼性を確保する |
| RQ-03 | Mock LLM モードを必須機能にする | テストを無料・決定的にし、API キーなしでも閲覧者が動かせるようにするため |
| RQ-04 | 入力本文はログに残さない | 公開・共有時の情報漏えい面を最小化するため（ダミーデータでも習慣として） |
| RQ-05 | Phase 6 の要件は MVP（FR-601〜615）と将来（FR-651〜657）に分ける | MVP の範囲を明確にし、AI レビュー・PR 本文生成は次の段階に回すため |
| RQ-06 | テストの合否は実装役の自己申告ではなく、独立した実行結果で判定する | AI の自己申告を根拠にしないため（[ADR-0001](./adr/ADR-0001-autonomous-development-loop.md)） |
