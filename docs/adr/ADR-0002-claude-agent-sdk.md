## 背景

- 初期設計では、無料枠と低単価を理由に、LLM として Gemini API を第一候補にしていた。
- [ADR-0001](./ADR-0001-autonomous-development-loop.md) で Phase 6（自律開発ループ）を追加し、コードを書く実装役が必要になった。
- 開発者は、アプリの内部で使う LLM を Claude に統一すると決定した。

## 1. 決定内容

| 用途 | 採用 | 備考 |
|---|---|---|
| チケット分析（Phase 1） | Claude API（Messages API ＋ 構造化出力） | TypeScript SDK `@anthropic-ai/sdk` |
| コーディングエージェント（Phase 6） | Claude Agent SDK | `CodingAgent` インターフェースの 1 実装 |
| Claude Code CLI | 初期の技術検証・比較評価の代替方式 | 先に本実装することは必須ではない |
| Gemini API | **現行実装の対象から除外** | 過去の検討記録として残す |
| ChatGPT | アプリの外の司令塔・技術レビュー役 | アプリの内部に OpenAI API は組み込まない |

## 2. Gemini から Claude へ変更する理由

| 観点 | 内容 |
|---|---|
| 1 社でそろう | チケット分析とコーディングエージェントを、同じ提供元・同じ API キー体系・同じ費用管理で扱える。費用の上限管理と説明が単純になる |
| 実装役の選択肢 | 権限制御・hooks・費用上限・隔離設定を型付きで持つ Agent SDK を使える |
| 構造化出力 | Messages API の構造化出力と、Zod 用のヘルパーが TypeScript SDK にある。「Zod を正とする」方針を保てる |
| 学習の焦点 | 複数社の API の違いを吸収する作業より、エージェントの制御・安全・評価・費用管理に時間を使える |

**失うもの**：Gemini の無料枠。Phase 2 の埋め込み（Embedding）を同じ API で賄える見込み。埋め込みの提供元は未決定とする（C-8）。

## 3. CLI と SDK の比較

| 比較軸 | Claude Code CLI | **Claude Agent SDK** |
|---|---|---|
| 組み込み方 | 外部プロセスとして起動し、結果の JSON を読む | TypeScript のアプリの中で直接呼ぶ |
| 公式の位置付け | ターミナルからの対話・単発の実行 | 自分のアプリに組み込み、自分で運用するプロセスの中で動かす |
| 上限の指定 | コマンド引数（最大ターン数・費用上限） | 型付きのオプション（最大ターン数・費用上限・中断） |
| 権限の判定 | 許可・拒否ルール、権限モード | 同左に加え、判定関数と hooks をコードで書ける |
| 隔離（sandbox） | 設定ファイルで指定 | オプションで指定できる（実際に効くかは未検証：C-5） |
| 終了理由 | 終了コードと結果 JSON | 結果メッセージの種別（ターン数超過・費用上限超過など） |
| テストのしやすさ | プロセス単位でしか差し替えられない | `CodingAgent` の裏を Mock に差し替えやすい |
| 実装の手間 | 最小 | 小〜中 |

## 4. SDK を採用する理由

1. **アプリ側で制御する設計（ADR-0001）に合う**：上限・中断・終了理由を型付きで受け取り、`LoopOrchestrator` の状態遷移にそのままつなげられる
2. **安全の仕組みをコードで書ける**：判定関数と hooks で、作業場所の外へのアクセスなどをアプリの規則で拒否できる。hooks の拒否は権限モードに関係なく効くと公式に記載がある
3. **既存の抽象化方針と同じ形にできる**：`CodingAgent` を定義し、SDK 版・Mock 版・（任意で）CLI 版を差し替えられる
4. **公式の使い分けに沿う**：自分のアプリに組み込むなら Agent SDK、と公式が案内している

### SDK を使うときに守ること（公式情報から）

| 注意点 | 対応 |
|---|---|
| `settingSources` を省略すると、利用者・プロジェクトの設定ファイルをすべて読み込む | **必ず `settingSources: []` を指定する**（ADR-0001 の S-10） |
| 判定関数は、ほかのルールで決まらなかったときにしか呼ばれない。自動承認系の権限モードでは呼ばれない | 自動承認系の権限モード（`bypassPermissions` など）は**使わない**。拒否は hooks と拒否ルールでも重ねて書く |
| 環境変数のオプションは、指定すると環境変数を丸ごと置き換える | 実装役に必要な最小限だけを明示して渡す |
| 返される費用はクライアント側の推定値で、請求の正本ではない | アプリの上限に余裕を持たせ、提供元側の利用上限と組み合わせる |

## 5. 費用管理

### 5.1 予算

| 単位 | 目標 | 備考 |
|---|---|---|
| 1 実行（Phase 6） | 最大 $1 | アプリ側で止める目標 |
| 1 日 | 最大 $3 | 同上 |
| 1 か月 | 最大 $10 | Claude API と Agent SDK を含む**プロジェクト全体の共通予算** |

これらはアプリ側で止めるための目標であり、**請求額の厳密な上限を保証しない**。

### 5.2 提供元側の上限

- 公式の案内に沿って、**本プロジェクト専用のワークスペースを作り、そこに利用上限を設定し、そのワークスペースの API キーを使う**方針とする。公式には、上限に達すると API リクエストが拒否されると記載がある。
- 設定は開発者が行う（Claude Code は手順の提示だけ）。
- **外部サービスの利用上限・請求管理は実装前に確認する。** 確認できるまで、実際の API 呼び出しを伴う実行を始めない。Mock での開発・テストは費用 0 で進められる。

### 5.3 1 回あたりの費用の目安

- チケット分析 1 回、Phase 6 の 1 実行の費用は、公式単価からの試算のみで**実測していない**。
- Phase 6 は Mock での開発を基本とし、実 API での実行は上限付きで少数だけ行う。

## 6. モデルの切り替え方針

- **モデル名をコードに直接書かない。** 用途（チケット分析・実装役・評価の採点役）ごとに、環境変数または設定ファイルで指定する。
- **最終的なモデルは評価結果で決める**（[評価設計](../evaluation.md)）。モデルの変更は軽微な設定変更として扱い、評価結果を記録すれば ADR は不要とする。ただし**提供元の変更は ADR にする**。

## 8. 既存の技術選定との整合

| 既存の決定 | 本 ADR での扱い |
|---|---|
| TypeScript ＋ Next.js ＋ React | 変更なし |
| LLM は Gemini API を第一とする | **本 ADR で変更**（→ Claude API） |
| LLM 呼び出しは `LlmClient` で包む | 変更なし。実装役は別の `CodingAgent` で包む |
| Zod を正とし、JSON Schema へ一方向に変換する | 変更なし。構造化出力を使っても、最終的な検証は必ず Zod で行う |
| Vitest ＋ Playwright、LLM は Mock | 変更なし。`CodingAgent` にも Mock を用意する |
| Phase 1 はローカル実行のみ | 変更なし |
| 既定モデル | **本 ADR で方針を決定**（設定で切り替え、評価で確定） |
| 比較用に別の LLM 提供元を追加するか | **本 ADR で解決**（現行実装は Claude に統一。他社の追加には新しい ADR が必要） |
| 月の費用上限 | 月 $10 をプロジェクト全体の共通予算として明確化 |
| 費用管理の単位 | 提供元側に本プロジェクト専用のワークスペースを作り、権限と請求を他と分ける |
