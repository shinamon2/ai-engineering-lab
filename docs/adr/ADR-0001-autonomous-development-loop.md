# ADR-0001: 自律開発ループ（Phase 6）の追加と、書き込み制約の例外

| 項目 | 内容 |
|---|---|
| 判断 ID | ADR-0001 |
| 日付 | 2026-10-29 |
| 承認状態 | **承認済み（Accepted）**。ただし「残課題」の技術的な未確認事項（T-1〜T-5）は**確定扱いにしない** |
| 実装状態 | **未実装**（設計段階）。自律開発ループは未完成 |
| 関連 | [Loop Engineering](../loop-engineering.md) / [Harness Engineering](../harness-engineering.md) / [セキュリティ設計](../security.md) / [ロードマップ](../roadmap.md) |
| 関連 ADR | [ADR-0002](./ADR-0002-claude-agent-sdk.md)（実装役の技術方式） |

## 背景

- 本プロジェクトの最終目標を、AI Ticket Analyzer（チケット分析）を中核に残したまま、「架空チケットを入力すると、分析 → 調査 → 計画 → 承認 → 実装 → テスト → 修正 → レビュー → PR 本文生成 → 最終確認」まで進む**ローカル自律開発エージェント**へ広げたい。
- 目的は 2 つ。①AI エージェントの制御・安全性・評価・費用管理を実践で学ぶこと、②それを説明・実証できるポートフォリオを作ること。「コーディングエージェントを自動で動かすだけのツール」にはしない。
- 既存の設計では、エージェントのツールを**読み取り専用**に限定している。コードを実装するエージェントにはファイル書き込みとコマンド実行が必要なので、この制約とそのままでは両立しない。

## 既存の決定との関係

| 既存の決定 | 内容 | 本 ADR での扱い |
|---|---|---|
| エージェントは読み取り専用 | エージェントのツールは読み取り専用とし、上限で必ず停止する | **Phase 3 には引き続き適用**。Phase 6 だけ、S-1〜S-10 の条件付きで書き込みを認める |
| Phase の順番 | 1 → 2 → 3 → 4 → 5 | Phase 番号は変えない。Phase 6 を追加し、推奨の実施順を「1 → 6（MVP）→ 2 → 3 → 4 → 5」とする |
| Phase 3 の多段エージェント | 分析を高度化するエージェント | 変更しない。Phase 6 を Phase 3 に吸収しない |
| 月の費用上限 | 月 $10 | 変更しない。プロジェクト全体の共通予算とする |
| push・公開・デプロイ | 人が判断する | 変更しない。Phase 6 の実装役は push・PR 作成・デプロイを行わない |

## 検討した選択肢

| 案 | 内容 | 長所 | 短所 | 判断 |
|---|---|---|---|---|
| A | 既存の Phase 3 を開発ループに置き換える | Phase が増えない | Phase 3 の「読み取り専用」の前提が崩れる。分析の高度化という Phase 3 の目的が消える | 不採用 |
| **B** | **Phase 6 を新設し、Phase 6 に限って書き込みの例外を設ける** | 既存の決定を壊さず、例外の範囲をはっきり書ける | 文書と Phase が増える | **採用** |
| C | Phase 5 の後に別プロジェクトとして作る | 既存の設計にまったく影響しない | チケット分析・費用ガード・評価基盤を再利用しにくく、着手が遅れる | 不採用 |
| D | ワークフロー全体を AI エージェントに任せる | 実装が最小 | 停止・承認・費用の制御を AI に委ねることになり、学習目的と安全方針に反する | 不採用 |

## 採用した方針

1. **Phase 6「自律開発ループ」を新設する**
   - 着手条件は Phase 1 の中核機能が完成していること。Phase 2〜5 の完了は条件にしない
   - 推奨の実施順は 1 → 6（MVP）→ 2 → 3 → 4 → 5
   - Phase 6 MVP に必要な最小の評価・テストは、Phase 4 を待たずに Phase 6 の中で作る
2. **工程全体の制御はアプリ側（自作の `LoopOrchestrator`）が持つ**
   - 状態遷移・修正回数・実行時間・費用・中断・失敗時の停止・実行履歴・人の承認はアプリが管理する
   - 実装役（`CodingAgent`）の内部ループは「1 回の実装・修正」の中に閉じ込める
3. **テストの合否はアプリが独立して判定する**
   - `TestRunner` が実際にコマンドを実行し、終了コードと結果で判定する。実装役の「テスト成功」という自己申告は根拠にしない
   - 修正は最大 3 回。初回の実装と修正回数は分けて数える
   - テスト未実行・実行失敗・タイムアウトは PASS にしない
4. **Phase 6 に限り、書き込みの例外を、下の条件（S-1〜S-10）付きで認める**

## 書き込み例外のセキュリティ条件（S-1〜S-10）

Phase 6 で実装役に書き込みとコマンド実行を許すのは、**次のすべてを満たす場合だけ**とする。1 つでも満たせない場合、実装役は起動しない（判定できない・異常時は拒否する＝fail closed）。

| # | 条件 |
|---|---|
| S-1 | 対象は架空チケットと、本プロジェクトで作ったダミーリポジトリだけ。実在の組織のリポジトリ・顧客情報・個人情報・秘密情報は扱わない |
| S-2 | 作業場所は本体リポジトリの外にある、実行ごとの使い捨てディレクトリ。本体リポジトリ・ホームディレクトリには書き込ませない |
| S-3 | エージェント SDK の権限制御だけを根拠にしない。**OS レベルの隔離**（sandbox またはコンテナ）を必ず組み合わせる |
| S-4 | 実装役を起動する前に、隔離が実際に効いていることを確認する（作業場所の外への書き込み・秘密情報の読み取り・外部ネットワーク接続がすべて失敗すること）。確認できなければ起動しない |
| S-5 | 実装役に渡す環境変数は必要最小限にする。ホストの秘密情報（SSH 鍵、クラウドの認証情報など）に届かないようにする |
| S-6 | 外部ネットワークへの接続は原則禁止。LLM API への通信だけを例外とする（実現方法は残課題 T-3） |
| S-7 | 実行できるコマンドは許可リスト方式（テスト・型チェックなど）。push・PR 作成・デプロイ・破壊的な操作は対象外 |
| S-8 | 人の承認ポイントを 2 つ置く。①実行開始前（計画・予算・対象の確認）②終了後（差分・テスト結果の確認）。成果を自動で本体へ取り込まない |
| S-9 | 実行時間・費用・ターン数・修正回数の上限を、アプリ側で必ず強制する |
| S-10 | 利用者のエージェント設定・本体リポジトリのエージェント設定を、実装役に読み込ませない |

詳細は [Harness Engineering](../harness-engineering.md) と [Loop Engineering](../loop-engineering.md) に書く。

## 判断理由

- **既存の決定を壊さない**：Phase 3 の「読み取り専用」と Phase 1〜5 の番号・内容をそのまま残し、例外の範囲を Phase 6 に限定して明文化できる（案 A・C より優れる）
- **学習目的に合う**：工程の制御・停止・承認・費用をアプリ側で実装すること自体が、本プロジェクトで学びたい「エージェントの制御・安全性・評価・費用管理」になる（案 D はこれを手放す）
- **早く着手できる**：Phase 6 は Phase 1 の中核（分析・費用ガード・評価基盤）だけに依存するため、RAG や多段エージェントを待たずに最終目標の中心部分に取り組める
- **安全の根拠を多重にできる**：書き込みを許す代わりに、OS レベルの隔離・事前確認・許可リスト・上限・人の承認を条件として重ね、1 つでも欠けたら起動しない形にできる

## 残課題（確定扱いにしない技術事項。T-1〜T-5）

| # | 内容 | 確認する時期 |
|---|---|---|
| T-1 | エージェント SDK から OS レベルの隔離を有効にできるか、ヘッドレス実行でも実際に効くか | Phase 6 実装の最初（隔離の確認タスク） |
| T-2 | 隔離の方式を sandbox にするか、コンテナにするか、両方にするか | T-1 の結果を見て判断 |
| T-3 | 外部ネットワークを禁止したまま、LLM API への通信だけを通す方法 | T-1 と同時 |
| T-4 | シェルのリダイレクトやファイルコピーなど、ツール単位の制限では検出できない書き込みを隔離で防げること | T-1 の確認項目に含める |
| T-5 | 作業場所の既定の置き場所（本体リポジトリの外のどこにするか） | Phase 6 実装開始時 |
