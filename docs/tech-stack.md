## 3. 主な選定理由

### 3.1 TypeScript ＋ Next.js ＋ React

| 評価軸 | 評価 | 理由 |
|---|---|---|
| 汎用性 | ◎ | 画面とサーバー処理を 1 つのリポジトリで書ける |
| LLM 習得 | ○ | Route Handler でサーバー側に LLM 呼び出しを閉じ込めやすい |
| 費用 | ◎ | ローカル実行なら費用 0。コンテナ実行環境などにも載せられる |
| 拡張性 | ○ | RAG・エージェントの処理もサーバー側の TypeScript で書ける |
| セキュリティ | ○ | `server-only` で API キーのクライアント混入を防げる。一方で依存パッケージ由来のセキュリティ更新が出るため、**継続的な更新が必須** |
| 説明しやすさ | ◎ | 広く知られた構成で、設計判断の説明に集中できる |

**比較した代替案**

| 代替案 | 不採用の理由 |
|---|---|
| Vite ＋ React ＋ 別立ての API | 構成が 2 つになり、Phase 1 の学習対象が LLM 以外に分散する |
| Python（FastAPI）＋ React | LLM・RAG のライブラリは Python が豊富だが、2 言語構成になる。Phase 2〜3 で必要性が出たら一部だけ Python 化を検討する |
| Remix / React Router | 十分モダンだが、説明のしやすさで Next.js を優先した |

### 3.2 Claude API の構造化出力

- 応答形式に JSON Schema を指定できる。TypeScript SDK には Zod 用のヘルパーがあり、検証済みの結果を受け取れる
- API 側では文字数・数値範囲・件数などの制約を使えない。SDK のヘルパーはこれらを説明文に移し、ローカルで検証する
- 応答が出力トークンの上限で途中で切れると JSON が不完全になる
- **方針: 最終的な検証は必ずアプリ側の Zod で行う**（TS-04）

### 3.3 Agent SDK と CLI の使い分け

比較と採用理由は [ADR-0002](./adr/ADR-0002-claude-agent-sdk.md) にまとめています。要点は次のとおりです。

- SDK は自分のアプリに組み込む用途、CLI はターミナルからの対話・単発実行の用途
- SDK は最大ターン数・費用上限・中断・権限の判定関数・hooks・隔離（sandbox）の設定を、型付きのオプションとして持つ
- **エージェント設定ファイルの読み込み（`settingSources`）は、省略すると利用者・プロジェクトの設定をすべて読み込む**ため、必ず空にする（[Harness Engineering](./harness-engineering.md)）
- SDK が返す費用はクライアント側の推定値で、請求の正本ではない

### 3.4 LLM SDK を直接使う理由

「まず公式 SDK で API の仕組みを直接理解し、抽象化は必要になってから入れる」方針です。Phase 1〜2 は公式 SDK を直接使い、自前の `LlmClient` インターフェースで包みます。Phase 3（エージェント）の開始時に、ループを自作するか既存の仕組みを使うかを再判断します。

### 3.5 Zod

- Zod スキーマから JSON Schema へ一方向に変換し、Zod 側を正とする
- JSON Schema から Zod への変換（実験的機能）は使わない
- 依存パッケージは npm 公開版だけを版固定で使い、Git の直接参照は使わない（[セキュリティ設計](./security.md)）

### 3.6 Vitest / Playwright

| ツール | 用途 | 理由 |
|---|---|---|
| Vitest | 単体テスト・スキーマ検証・評価ロジック | TypeScript で設定が少なく高速 |
| Playwright | E2E（入力 → 分析 → 表示） | Mock LLM モードで、無料かつ結果が毎回同じテストにできる |

### 3.7 ホスティング（TS-U3・未決定）

| 候補 | 評価 |
|---|---|
| **ローカル実行のみ** | **Phase 1 はこれで確定**。閲覧者には動画・スクリーンショットで示す |
| コンテナ実行環境（マネージド） | 公開デモを出す場合の第一候補。秘密情報の保管サービスで API キーを管理する |
| その他のホスティングサービス | 利用規約・支出管理の機能を確認してから判断する |

**公開デモの最大のリスクは「他人が使って API 料金が増える」こと**です。公開する場合は、アクセス制限・回数制限・提供元側の利用上限の 3 重で守ります（[セキュリティ設計](./security.md)）。

### 3.8 ベクトル DB（Phase 2・TS-U4・未決定）

| 候補 | 評価 |
|---|---|
| ファイル保存 ＋ 自前のコサイン類似度計算 | 架空仕様書 10〜30 本なら十分。仕組みを理解する学習に最適。**Phase 2 前半の推奨** |
| SQLite ＋ ベクトル拡張 | ローカル完結。拡張の成熟度を確認してから判断 |
| Postgres ＋ pgvector（マネージド） | 本番に近い RAG を示したい場合の候補 |

## 4. 費用の考え方

- 月 $10 を、チケット分析と Phase 6 を合わせた**プロジェクト全体の共通予算**の目標とする
- Phase 6 の上限は 1 実行 $1（目標）/ 1 日 $3
- 具体的な単価は公式の料金ページで実装直前に確認し、評価結果と合わせてモデルを選ぶ
- Phase 6 の 1 実行あたりの費用は未実測。Mock の実装役で開発し、実際の API を使う実行は少数に抑える
- 費用上限の多層防御は [セキュリティ設計](./security.md)、Phase 6 の上限は [Harness Engineering](./harness-engineering.md) を参照

## 5. 決定事項

| ID | 決定内容 | 判断理由 |
|---|---|---|
| TS-01 | TypeScript ＋ Next.js（App Router）＋ React を採用 | 汎用性・説明しやすさ・1 リポジトリでのフルスタック構成 |
| TS-03 | LLM 呼び出しは `LlmClient` インターフェースで包む | 提供元・SDK の差し替えと、Mock 化によるテストのため |
| TS-04 | Zod を出力スキーマの単一の正とし、JSON Schema へ一方向に変換 | API 側で強制されない制約があるため、最終検証は必ず Zod で行う |
| TS-05 | Vitest ＋ Playwright、LLM は Mock で実行 | テストを無料・決定的にするため |
| TS-06 | Phase 1 はローカル実行のみ | 公開時の費用・不正利用のリスクを Phase 1 から抱えないため |
| TS-07 | チケット分析は Claude API、Phase 6 の実装役は Claude Agent SDK を使う | [ADR-0002](./adr/ADR-0002-claude-agent-sdk.md) |
| TS-08 | モデル名はコードに直接書かず、用途ごとに設定で切り替える | 評価結果でモデルを選び直せるようにするため |
| TS-09 | API の認証は、本プロジェクト専用のワークスペースで発行した API キーを使う | 利用上限をワークスペース単位で設定でき、権限と請求を他と分離できるため |

（TS-02 は ADR-0002 で置き換えたため欠番です。）
